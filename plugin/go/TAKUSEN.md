# Takusen native module

This branch customizes the Go plugin as Takusen's Canopy-native state machine. It adds consensus-validated Nitro enclave registration, governed protocol parameters and settlement domains, block-effective bonded-servicer economics, producer rewards, EVM deposit observations, domain-scoped credit reservations, deterministic model assignments, signed execution receipts, and atomic settlement observations.

`takusenRegisterServicer` is one ordinary fee-paying transaction signed by the servicer owner. It atomically carries the bond, models, one nonzero EVM payout address used by every settlement domain, complete Nitro COSE document, Ed25519 public key and proof of possession, nonce, canonical owner-bound user data, and derived tee key ID. During block delivery every validator applies bounded CBOR/COSE/X.509 validation against the trust root and PCR tuple in protocol state, using only the block's consensus timestamp and height for freshness and policy selection, before it writes both the enclave and active servicer records and locks the bond. It rejects an owner that is already registered. The document is capped at 16 KiB; Core grants only this message a 20 KiB outer-transaction ceiling instead of raising the generic 4 KiB limit. Domain activation never changes servicer registration. There are no per-validator registration observations, quorum counters, local root files, wall-clock reads, standalone enclave-registration transaction, per-domain payout mapping, or compatibility message.

Existing owners use one sparse, revision-checked `takusenManageServicer` transaction containing only changed configuration, exact bond target, or enclave-rotation components. Model IDs are canonicalized, and any changed components may still commit atomically. Rotation carries a complete fresh attestation, registers the replacement key, switches all new assignments to it, and marks the previous key draining. A draining key accepts only receipts for assignments already frozen to it, and routine rotation needs no finalize or cleanup transaction. A bond decrease moves value into the account's single cliff-locked balance; after its governed release height the normal account spendability calculation includes it automatically, without a withdrawal transaction. Emergency enclave revocation is an incident-bound auxiliary candidate certified by validator vote extensions rather than a fee-paying transaction; certification revokes the key and atomically deactivates its associated servicer. Producer payout configuration and cross-chain funding remain separate transactions because they belong to different authorities.

Finalized deposits create replay-protected, settlement-domain-scoped records and increment the requester's credit account for that domain only after strict stake-weighted validator quorum. Off-chain EIP-712 authorization atomically reserves witnessed credit. Execution records reservation spend, and one exact `settleBatch` transaction moves spend to settled credit and releases the unused budget. A `non_answer` receipt preserves positive authenticated provider spend when post-usage parsing or tool orchestration fails below the assignment ceiling; it carries no output, is terminal, and settles through the same EVM non-answer status as an over-budget execution. These records are queryable under `/v1/takusen/deposits`, `/credits`, and `/reservations`.

Protocol parameters use Canopy's native `changeParameter` proposal lifecycle and require a complete canonical document with a monotonic revision. Parameters cover model/provider allowlisting, the bounded Nitro trust-root set, PCR policies, fees/margins, deadlines, the minimum servicer bond, slash rates, epoch emissions, treasury allocation, governed settlement domains and their abandonment delays, and bridge limits. Each active-to-inactive transition snapshots that domain's delay, which cannot be configured below 86,400 seconds. Strict greater-than-two-thirds quorum and the one-hour validator epoch schedule are protocol invariants rather than governed knobs. Provider prices and per-model budget schedules are not governed: the provider-reported cost authenticated and signed by the TEE is authoritative, and each assignment's all-in cap is its deterministic equal share of the request budget. A request-specific authorization expires at a governed Canopy height; its unique request ID and one-shot state transition provide replay protection. EOA authorizations use the state-independent direct path, while ERC-1271 observations bind one safe settlement-chain block number/hash into the quorum subject. Request admission spends only finalized credit, never a provisional low-finality deposit. Requester-selected agreement thresholds are display metadata only: every assignment runs or reaches its deterministic terminal state before request-level settlement. Every remaining observation and conflict claim is keyed by an immutable validator-set ID and epoch and stores the observer's snapshot weight plus the snapshot total, so votes cannot cross snapshots or gain weight retroactively. A minority finalization vote leaves the request in settlement discovery until quorum or a valid certificate completes the terminal transition.

The canonical TAKU reward-chain domain's `LockedForCanopy` calls mint native balances only after safe-finality exact independent call/event verification and quorum, with transaction-hash, nonce, per-transfer, and per-epoch replay/risk limits. Native burns create immutable release records and remain pending until validators observe their safe canonical call/event. If reward or burn relay spans a validator rotation, the current committee may re-certify the same immutable allocation or burn fields; the epoch number and burn ID remain the replay nullifiers. Servicer bond targets take effect in the same management transaction. Authenticated invalid receipts apply their typed penalty inside receipt processing and consume active bond before still-locked account collateral. Terminal assignment expiration is applied directly and incrementally in BeginBlock from finalized height, without a fee-paying transaction or redundant vote-extension certificate, and never slashes. Other slashable facts enter consensus as typed candidates with fixed evidence schemas rather than a free-form reason transaction. Every plugin transaction pays the governed native send fee inside the same atomic state transaction as plugin delivery. Producer payout mappings are restricted to current/prepared validators or identities recorded by consensus after actual block production.

Every validator epoch has a consensus-time schedule. If it starts at S, Core freezes the exact N+1 candidate at S + 1,200 seconds and the normal boundary is always T = S + 3,600 seconds. An unchanged weighted roster advances at T without changing the EVM validator-set ID. A changed roster also advances at T on the happy path once every frozen settlement domain has finalized the matching scheduled roster; only a missed readiness barrier extends a failed epoch. Authority advances before reward accounting: the boundary writes an immutable `EpochAuthorization` snapshot, and a later open-phase block finishes at most one bounded reward job. Its digest exactly matches `TakusenToken.mintEpoch`; allocations are proportional to eligible blocks and include the governed treasury share. Buyback automation is not part of this module.

## EVM BDN proof export

Operational EVM observations, settlement facts, validator rotation, retirement, bridge, and reward effects enter automatic vote extensions as typed candidates. They are not optional variants in a validator-submitted signature-share transaction. Explicit governance approval alone uses the narrow `takusenGovernanceVote` transaction, bound to one proposal ID, digest, and validator-set ID. Once strict greater-than-two-thirds stake certifies a candidate, the plugin stores the resulting `QuorumProof` under `/v1/takusen/quorum-proofs/{proof-id}`.

Auxiliary certificates follow a separate Core-owned trust boundary. Canopy validates their complete candidate envelope, aggregate signature, historical signer committee, and strict quorum before `BeginBlock`. The plugin does not repeat that cryptographic verification or receive the historical roster; it persists the already-validated signature and bitmap for relay and derives informational signer weights and epoch attribution from its immutable epoch snapshots. External watcher candidates live in a deterministic bounded Core memory pool, while the validator watcher is their sole durable outbox and republishes them after a Core restart. Native candidates remain reproducible from committed state.

The roster uses Core's canonical committee order: descending raw stake, then descending validator address for ties. Bitmap bit `i` (least-significant bit first) selects roster member `i`. A persisted proof contains only its identity and digest, validator-set ID, signer bitmap, EIP-2537 aggregate signature, signed/total weights, and creation height. The active validator set supplies the roster and weighted EIP-2537 public keys needed by each domain verifier.

Prepared validator rotations preserve each exact raw uint64 Canopy voting power in the verifier's uint96 field. Normalized or approximate rosters are rejected, including any encoding that would turn an exact-two-thirds coalition into strict quorum. Rotation claims and direct proof indexes include the settlement domain. The outgoing committee schedules the frozen roster independently on every governed verifier, and validators mark a domain resolved only after that exact state is finalized on the EVM chain. Each verifier stores two parity-selected roster slots and derives the active set from its scheduled ID and activation timestamp, so N+1 becomes authoritative at T without promotion, copying, cancellation, or cleanup. A lagging domain may still install the same original certified N+1 after T; Native remains on N until every frozen domain resolves and then advances once. No historical generation, EVM-local block height, or coordinator decision can select or resurrect a different committee.

Consensus range pages use a prefix-bound full-key continuation cursor backed by native Pebble and transaction-index seeks. Core excludes the cursor in the requested direction, and the plugin rejects duplicate, reordered, or out-of-prefix pages. Direct rotation-proof, pending-reward, pending-bridge-burn, provisional-reservation, active-servicer, timeout-cursor, and settlement-cursor indexes avoid permanent-history scans in handoff, relay, deposit resolution, enclave revocation, timeout, and settlement work.

The EVM proof argument is `abi.encode(bytes aggregateSignatureEIP2537, bytes signerBitmap)`. `plugin/go/contract/quorum_vector_test.go` and Takusen's `contracts/test/BDNQuorumVerifier.t.sol` share a fixed cross-language vector.

The core/plugin begin-block request includes the previous finalized block hash. Takusen uses that trusted value with the request input hash and model identifier to derive assignments.

Run the two-validator development network from the Canopy repository root:

```sh
docker compose -f plugin/go/compose.yaml up -d --build
```

The query RPC is at `http://localhost:50002`; the Takusen plugin RPC is at `http://localhost:50010`. The second node exposes query RPC `40002` and plugin RPC `50011`. Host publication is loopback-only. Inside each container the plugin uses `TAKUSEN_PLUGIN_RPC_TOKEN`; authorized clients send the same value as `CANOPY_PLUGIN_TOKEN`. Non-loopback listeners without a token are refused. The HTTP server bounds accepted connections, concurrent handlers, request identities, and subscribers; SSE writes have deadlines and streams expire after 30 seconds.

Run the native consensus integration test after both nodes are healthy:

```sh
cd plugin/go
TAKUSEN_E2E=1 go test -run TestTakusenConsensusE2E -v -count=1 -timeout=5m
```

If the fixture enclave key is not already committed, set `TAKUSEN_E2E_REGISTRATION_BUNDLE` to the fresh JSON response fields from its NSM attestation endpoint plus the request's `nonce` and canonical owner-bound `userData`. The test submits that complete evidence and bond as one owner-signed registration transaction; it fails rather than skipping registration when the bundle is absent. It then commits registration → deposit → reservation → authorization → assignment → execution → settlement → release through both validators. The local validator keys are fixture keys from `.docker/volumes`; production validator observers must run independently and must not expose their keys to an application process.
